## 第 1 部分：从零设计

### 1.1 一句话定位
**用户感受到的是"一个曲库"，不是"四个平台"。** 音源是实现细节，就像 Apple Music 不会告诉你歌曲文件存在哪个 CDN 节点。聚合 App 最容易犯的错误，是把"有几个平台"做成了界面的主轴：到处都是平台切换，搜索结果里同一首歌重复四遍，用户要自己判断哪个能播。

所以第一原则是：

| 原则 | 含义 |
| --- | --- |
| 一首歌只出现一次 | 搜索、榜单、歌单里，不同平台的同一首歌合并为一行，来源只用一个小标记表示 |
| 默认就能播 | 点播放时由"解析器"自动选出能完整播放、音质最好的版本；用户不需要知道换过源 |
| 平台只在需要时出现 | 只在三个地方显式出现：歌曲"信息/音源"面板、账户设置、浏览页的"来源"筛选 |
| 内容是主角 | 封面和文字占据视觉重心，界面元素（按钮、分隔线、背景）尽量退后 |

### 1.2 核心概念模型

```
Work（作品）          ← 用户看到、收藏、加入歌单的对象
 ├─ Rendition（版本）  ← 某个平台上的具体曲目：netease:347230、qq:003OUlho2HcRHC …
 │    ├─ 可用性：完整 / 试听 / 无版权 / 需会员
 │    ├─ 可用音质：标准 … 无损 / Hi-Res
 │    └─ 元数据质量：是否有 ISRC、逐字歌词、翻译、高清封面
 └─ 合并键：ISRC 优先；否则 规范化(歌名) + 规范化(主歌手) + 时长 ±3s
```

- **规范化**：全半角、繁简、大小写统一；去掉 `(Live)`、`- Remastered`、`feat.` 等后缀后再比较，但这些后缀会作为"版本差异"降低匹配分，不会把 Live 版和录音室版当成同一首。
- **歌单/资料库里存的是 Work**，同时缓存已知的 Rendition 列表。某个平台下架了，Work 还在，自动换到别的版本。
- **元数据择优**：封面取最高清的（通常是 Apple），歌词取最好的（逐字 > 行级，有翻译优先），播放取能完整播放且音质最高的。三者可以来自不同平台。

### 1.3 解析器（播放时选版本）

```
score = 可用性权重(完整 1000 / 试听 100 / 不可用 0)
      + 音质分(Hi-Res 60, 无损 50, 极高 30, 标准 10)
      + 用户平台偏好(0–20)
      + 匹配置信度(ISRC 命中 +30，时长差每秒 -5)
      - 最近失败惩罚
```

- 播放当前曲时，后台**预解析下一首**（URL 有效期内缓存），切歌零等待。
- 用户可以在"音源"面板里**手动固定**某个版本，固定结果写入资料库。
- 解析失败给出可执行的下一步："登录 QQ 音乐可完整播放"，而不是"播放失败"。

### 1.4 信息架构

参照 Apple Music 的四个一级入口，去掉"平台"这一层：

| 入口 | 内容 |
| --- | --- |
| **立即收听** | 继续播放、最近播放、为你推荐（来自已登录平台的每日推荐/私人歌单，合并展示）、最近加入资料库 |
| **浏览** | 新歌、榜单、精选歌单、心情/场景分类。顶部一个"来源"下拉筛选（默认"全部"），不用分段控件 |
| **资料库** | 本地统一曲库：喜欢的歌曲、歌单（自建 + 从任意平台导入）、专辑、歌手、下载。这是聚合 App 最有价值、单一平台给不了的东西 |
| **搜索** | 统一结果：最佳结果 → 歌曲（已合并）→ 专辑 → 歌手 → 歌单；粘贴任意平台链接直接打开 |

另有：**歌手页**（热门歌曲、专辑、单曲 EP）、**专辑页**、**歌单页**、**正在播放**、**设置/账户**。

### 1.5 布局

**桌面（≥ 900px）**：Apple Music for Mac 式三段

```
┌──────────┬─────────────────────────────────────────┐
│ 侧边栏    │ 顶部：‹ › 历史导航  ·  搜索框（⌘K）       │
│ 立即收听  │                                         │
│ 浏览      │      内容区（大标题 34pt + 货架/网格/列表）│
│ ─────     │                                         │
│ 资料库    │                                         │
│  歌曲     │                                         │
│  专辑     │                                         │
│  歌单 ▸   │                                         │
│ 下载      │                                         │
├──────────┴─────────────────────────────────────────┤
│ 播放条：封面 歌名/歌手 │ ⏮ ⏯ ⏭  进度 │ 歌词 队列 音量 │
└────────────────────────────────────────────────────┘
```

- 侧边栏用半透明材质（vibrancy），内容区不透明，层级靠材质区分而不是阴影。
- 歌词和队列从右侧滑出，作为内容区的一部分（不遮挡侧边栏）。

**手机（< 640px）**：iOS Music 式

- 底部 4 个标签：立即收听 / 浏览 / 资料库 / 搜索；设置放在"立即收听"右上角头像里。
- 迷你播放条浮在标签栏上方；上滑或点击展开为全屏"正在播放"，封面做共享元素过渡。
- 大标题随滚动收缩为导航栏小标题。
- 所有可点区域 ≥ 44×44pt，安全区适配。

**平板 / 窄桌面（640–900px）**：侧边栏折叠为图标栏。

### 1.6 视觉语言

| 维度 | 规范 |
| --- | --- |
| 字体 | `-apple-system, "SF Pro", "PingFang SC", "Segoe UI Variable", "Microsoft YaHei UI", sans-serif`；字号阶梯 34 / 28 / 22 / 17 / 15 / 13 / 11，字重只用 400 / 500 / 600 / 700 |
| 颜色 | 浅色/深色两套语义色：`label` 四级灰度、`fill` 四级、`separator` 发丝线；**一个**强调色（默认 Apple Music 红 `#fa2d48`，可改） |
| 来源标识 | 不用平台品牌色大面积着色。只用 6px 圆点 + 简称，统一灰度，悬停才显示完整平台名 |
| 圆角 | 4（小标签）/ 8（封面小图、按钮）/ 12（卡片、封面大图）/ 20（面板、底部抽屉） |
| 间距 | 4pt 基线、8pt 网格；页面左右边距 桌面 32 / 手机 20 |
| 材质 | 只在侧边栏、播放条、弹出层使用模糊材质；正文区域纯色 |
| 封面 | 永远保持 1:1，加 0.5px 内描边防止白封面融进背景；正在播放页背景用封面取色做流动渐变 |
| 图标 | 一套线性图标，1.75px 线宽，24 网格；激活态改为填充，而不是换颜色 |

### 1.7 动效

- 统一使用弹簧曲线（响应时间 0.35s、阻尼 0.85 左右），不使用线性和夸张回弹。
- 只动 `transform` 与 `opacity`；列表进入用 20ms 级错峰，最多前 12 项。
- 迷你播放条 ↔ 正在播放：封面共享元素过渡；下拉手势可中途取消，跟手。
- 歌词：当前行放大并清晰，其余行降低不透明度并轻微模糊；逐字歌词用渐变扫光。
- 尊重"减少动态效果"：关闭位移和模糊，只保留淡入淡出。

### 1.8 关键组件

| 组件 | 规范 |
| --- | --- |
| 歌曲行 | 40px 封面 · 歌名（可带"E"/"试听"/"无损"小标签）/ 歌手 · 专辑（桌面）· 时长 · `…` 菜单。行高 56（桌面）/ 60（手机） |
| 货架（Shelf） | 横向滚动 + scroll-snap，桌面显示左右箭头，标题右侧"查看全部" |
| 来源筛选 | 下拉菜单或横向滚动的胶囊（chips），**不用分段控件**——分段控件适合 2–4 个互斥视图，不适合数量会增长的筛选项 |
| 上下文菜单 | 播放下一首 / 加入队列 / 加入歌单 / 喜欢 / 下载 / 前往专辑 / 前往歌手 / 分享 / 音源 |
| 底部抽屉 | 手机端所有二级操作都用抽屉，固定高度档位（半屏 / 全屏），可下拉关闭 |
| 状态 | 加载用骨架屏（与真实布局同尺寸，避免跳动）；空状态有插画式图标 + 一句话 + 一个主操作；错误给出可执行的修复按钮 |

### 1.9 正在播放

- 桌面：左侧大封面 + 控制，右侧歌词；手机：封面页 ↔ 歌词页左右切换或点击切换。
- 顶部只显示一行"来源 · 音质"小字（例如 `QQ 音乐 · 无损`），点开是"音源"面板：列出所有版本、各自可用性和音质，可一键切换或固定。
- 试听版本用醒目但克制的标签，并直接给出"换一个完整版本"按钮。

### 1.10 账户与凭证

- 账户页列出所有平台，每个平台一行：状态（未登录 / 已登录 · 会员到期日）、登录方式（扫码 / 短信 / 网页登录 / Cookie）。
- 登录方式按平台能力动态出现，优先顺序：扫码 > 短信 > 应用内网页登录 > 手动粘贴 Cookie。
- 凭证只存本机（桌面/手机）或自托管服务器，权限 0600，不进日志。

### 1.11 平台集成

| 平台 | 必须做好的系统集成 |
| --- | --- |
| Windows | SMTC 媒体控制（音量键浮窗、锁屏）、任务栏缩略图按钮、托盘、桌面歌词、Mica 标题栏、全局快捷键 |
| Android | **原生媒体会话 + 前台服务**（WebView 里的 `<audio>` 进后台会被系统杀掉），通知栏/锁屏控制、耳机线控、音频焦点（来电暂停） |
| Web | PWA 可安装、Media Session API、键盘快捷键、单二进制自托管 |

### 1.12 技术架构

```
┌────────────── UI（Svelte 5，三端共用）──────────────┐
│  视图层  ←  状态（Work/队列/资料库） ←  Transport     │
└───────────────────────┬─────────────────────────────┘
          HTTP（Web）/ IPC（Tauri）   同一套接口
┌───────────────────────┴─────────────────────────────┐
│ Rust core                                            │
│  Source trait × N  →  Matcher（合并 Work）           │
│                    →  Resolver（选版本、预解析）       │
│  Library（SQLite：Work、Rendition、歌单、播放记录）    │
│  Cache（元数据 / URL / 封面）  Downloader  Credentials │
└──────────────────────────────────────────────────────┘
          Player：桌面/Web 用 <audio>；Android 用原生 Media3
```

- 资料库放在 Rust 侧的 SQLite 里，而不是浏览器 `localStorage`，这样三端格式一致，可以导入导出。
- 合并和解析都在 core 里做，前端只拿到"已合并的 Work + 推荐版本"，保持前端简单。

| 指标 | 目标 |
| --- | --- |

## 第 2 部分：现有设计的缺陷（对照第 1 部分）

> 说明：本节的每一条都标注了核实方式。**【实测】**＝我在线上 `https://music.camvan.xyz` 或本地用浏览器/命令实测过；**【读码】**＝由静态读码得出、未运行时验证。实测时使用的账号未登录任何平台。

### 2.1 核心差距概览

| 第 1 部分的设计意图 | 现状 | 差距等级 |
| --- | --- | --- |
| 一首歌只出现一次（Work 合并） | 同一首歌按平台重复出现 4 次，用户自己分辨 | 🔴 结构性 |
| 有"资料库"层（收藏、歌单、本地曲库） | **完全没有**：没有喜欢、没有收藏、没有自建歌单、不能导入他站歌单 | 🔴 结构性 |
| 元数据择优（封面/歌词/音源各自取最优） | 谁被点到就用谁的元数据，不做择优 | 🟠 重要 |
| 播放时自动选最优版本并预解析下一首 | 只做"当前音源失败后去别的源找"，不预解析、不择优 | 🟠 重要 |
| 桌面三段式（侧边栏 + 内容 + 播放条） | 顶栏 + 单列内容，无侧边栏、无资料库入口 | 🟠 重要 |
| 来源筛选用下拉/胶囊 | 用**分段控件**，且平台切换被提升为界面主轴 | 🟠 重要 |
| 资料库存 Rust 侧 SQLite，三端一致、可导入导出 | 全部状态散在 `localStorage`（7 个不同 key），换设备即丢 | 🟠 重要 |
| 设计令牌覆盖字号/圆角/层级/间距 | 有颜色/圆角/时长变量，但字号 24 种、圆角 22 种、z-index 15 种、间距全硬编码 | 🟡 一般 |
| 平台系统集成（SMTC / Android 前台服务） | Web Media Session 只做了一半；桌面无 SMTC；Android 后台播放无保障 | 🟠 重要 |
| 首屏 JS ≤ 80KB | 首屏 JS 134KB（gzip 45KB）+ CSS 79KB，无按需拆分 | 🟡 一般 |

### 2.2 信息架构：缺少"资料库"这一层 【实测】

第 1 部分把"资料库"放在四个一级入口之一，因为它是聚合 App 相对单一平台**唯一不可替代**的价值——单一平台的歌单会有版权灰掉，多源聚合的资料库不会。

现状（grep `喜欢|收藏|favorite|library|资料库` 命中 **0**）：

- 没有"喜欢/收藏"。
- 没有自建歌单。
- 不能把他站歌单保存为本地歌单（只能当场浏览、当场播放）。
- 没有本地统一曲库视图。

用户能做的持久化只有三样：**最近播放**（`recent.svelte.ts`）、**搜索历史**（`history.svelte.ts`）、**上次播放会话**（`player` 的 `shiyin.session`）。全都是浏览器本地、单设备的。

后果：用户收藏一首歌的唯一办法是去原平台收藏——回到"记住哪个平台有哪首歌"的老路，聚合的价值被抵消一半。

### 2.3 概念模型：没有 Work / Rendition 【实测】

第 1 部分要求"搜索、榜单、歌单里不同平台的同一首歌合并为一行"。

实测：搜"晴天"，结果列表里连续出现

```
晴天 (原唱 周杰伦)  网易  RyaVocal
晴天                酷我  周杰伦
晴天                QQ   周杰伦
晴天                 Apple 试听  周杰倫
晴天 (女声版))       网易  GYBeat
晴天 (Live)          酷我  周杰伦
...
```

同一个"周杰伦《晴天》"至少出现 3–4 行，用户要自己判断点哪个。榜单、首页"最新音乐"同样如此。

根因在 Rust 侧：`Sources::search_all`（`crates/core/src/source.rs:246`）只做 `interleave`（各源结果交替穿插），**没有任何合并或去重**。`Track` 也没有 ISRC 字段（`crates/core/src/model.rs`）。合并能力从数据模型开始就是缺的。

> 注：`find_candidates_for`（`source.rs:318`）里有基于 `歌名 == 歌名 && artist.contains` 的匹配逻辑，但它是**播放兜底时单首查询**用的，没有用在搜索结果合并上，也没有 ISRC/时长的完整匹配。

### 2.4 解析器：只有"失败兜底"，没有"主动择优" 【读码】

第 1 部分：点播放时自动选"能完整播放 + 音质最好"的版本，并预解析下一首。

现状（`web/src/lib/player.svelte.ts:192-212`）：

```ts
const r = await api.songUrl(t.id, settings.playLevel, t.source);
if (r.trial && settings.autoFallback) { ...  // 只有"拿到试听"才去找替代
```

- 是"**先按用户点的那一行**取 URL，拿到试听或报错才去找别的源"，而不是"一上来就比较各版本选最优"。
- 换源逻辑在**前端**（`#tryFallback` 调 `/api/match`），不在 core；换源结果只进内存缓存。
- **不预解析下一首**：实测切歌时 `songUrl` + 可能的 `/api/match` 都要现场等（上一轮日志里 `/api/match` 单次就要数秒）。
- 音质选择是"全局单一档位"（`settings.playLevel`），不是"这首歌能拿到的最高档"。

### 2.5 布局与导航 【实测】

**桌面端没有侧边栏**（`App.svelte:87-133`）：整个应用是一个顶栏 + 单列内容区，与第 1 部分的"三段式"差距明显。功能入口被塞进右上角 5 个图标按钮（最近播放、播放列表、下载、设置、头像），信息密度高但发现性差。

**来源切换被过度强调**：分段控件（segmented control）出现在首页头部、搜索页、搜索结果页三处（`Home.svelte`、`MobileSearch.svelte`、`App.svelte` 的 `src-tabs`）。第 1 部分明确指出：分段控件适合 2–4 个**互斥视图**，不适合数量会增长的**筛选项**——每加一个音源就要重排一次，正是上一轮"5 个 tab 挤两行"bug 的来源。应改为下拉或胶囊。

**移动端术语不统一**：同一页被叫"主页"（`Home.svelte:35`）、"首页"（`App.svelte:93`）、"发现"（`MobileTabBar.svelte:32`）三个名字。

### 2.6 视觉语言：令牌体系不完整 【读码】

有颜色、圆角、时长、安全区变量（`app.css:1-55`），但：

| 维度 | 现状 | 问题 |
| --- | --- | --- |
| 字号 | 无 `--fs-*` 变量，全手写，去重后 **24 种**值 | 无法系统调整，出现 8px/9px/10.5px 这类非阶梯值 |

### 2.7 性能缺陷

**🔴 虚拟列表行高常量与实际不符【实测】**：`TrackList.svelte:33` 写死 `const ROW = 56`，但 `@media (max-width: 760px)` 下行高是 `58px`（`:483`）。我把窗口缩到 700px 实测：真实行高 **58px**，而 `.list` 容器高度按 56px 算（21 首 → 计算 1176px，实际 `listH=1792`，含 overscan）。`measure()`（`:48`）也用 56 算窗口位置。

- 影响：760px 以下每行误差 2px，滚动越深偏移越大，可能出现空白行/错位；总高被低估约 3.4%。
- 这是**功能性 bug**，不是观感问题。

**🟡 首屏未做任何按需拆分【实测】**：`App.svelte:2-20` 静态 import 全部 18 个组件，`vite.config.ts` 无 `manualChunks`、无动态 import。实测产物 `main-*.js` = 134,743 B（gzip **45,235 B**）、`main-*.css` = 79,137 B（gzip 13,486 B），且在 `main.js` 里能 grep 到"扫码登录""迷你播放器"等字符串——**从不打开的登录/设置/播放面板全在首屏包里**。

**🟡 封面图只对网易云裁剪【读码】**：`format.ts:22-28` 的 `img()` 只对 `126.net` 追加 `?param=`，QQ/酷我/Apple 一律用原图。列表里 `img(t.cover, 40)` 会下载原始大图（实测酷我封面 500px、QQ 300px、Apple 600px），滚动时流量与解码成本显著。

**🟡 无尺寸/懒加载的图片较多**：`use:fade` 已保证淡入正确（实测无可见的加载失败或卡在透明的图），但若干部位缺 `loading="lazy"`、缺 `width/height`（CLS 风险）。

### 3.4 P3：架构演进（这是第 1 部分与现状之间真正的鸿沟，需要排期）

**3.4.1 数据模型：引入 Work / Rendition**

```rust
// crates/core/src/model.rs 新增
pub struct Work {
    pub key: String,          // isrc:<ISRC> 或 fp:<归一化hash>
    pub title: String,
    pub artists: Vec<Artist>,
    pub duration_ms: u64,
    pub rendition_ids: Vec<String>,   // "source:id"
}
pub struct Rendition {
    pub id: String, pub source: String,
    pub isrc: Option<String>,
    pub availability: Availability,
    pub max_level: String,
    pub has_lyrics: bool, pub has_sync_lyrics: bool,
    pub cover_hint: String,
}
```

- `Track` 增加 `isrc: Option<String>`（各适配器尽力解析：QQ/Apple 通常有，网易/酷我需要按需查询）。
- 合并函数在 core：`fn merge_works(tracks) -> Vec<Work>`，键 = ISRC 优先，否则 `归一化(title) + 归一化(主歌手) + 时长 ±3s`。
- 接口新增 `GET /api/search/merged`，前端搜索结果默认用它；保留原接口给"按平台浏览"。

**3.4.2 解析器下沉到 core**

```
GET /api/resolve?work=<key>&level=lossless   → { track, url, why }
```
- 内部：按第 1.3 节打分选版本；结果进 core 缓存（URL 有效期）。
- 新增 `POST /api/resolve/preload`：传下一首 work key，异步预热（前端切歌前调用）。
- 前端 `player.svelte.ts` 的 `#tryFallback` 删除，改为只在 `resolve` 失败时提示"登录 X 可完整播放"。

**3.4.3 资料库（SQLite）**

```
library.db: likes | playlists | playlist_items | works | renditions | plays | downloads
```
- Rust 侧 `rusqlite`（bundled），三端共用；Web 版存服务器数据目录。
- 接口：`/api/library/{likes,playlists,plays}` 增删查；导入他站歌单时把每首解析为 Work 存 `renditions`。
- 前端：资料库视图 + 歌曲行 `…` 菜单加"喜欢 / 加入歌单"；`localStorage` 里只留纯 UI 偏好（主题、音量、歌词字号）。
